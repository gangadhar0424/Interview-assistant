## D-01 Web stack: Next.js + React + TypeScript — Accepted
- **Context:** Authenticated dashboard + wizard; desktop UI also React.
- **Decision:** Next.js (App Router), React, TS strict; generated API client.
- **Alternatives:** Vite SPA; Remix; SvelteKit.
- **Reasoning:** Ecosystem, hiring, code/type sharing with Tauri React UI. SSR is marginal here but harmless.
- **Consequences:** Node build tooling; keep business logic in API, not in Next server actions.

## D-02 Backend: Python + FastAPI modular monolith — Accepted
- **Context:** AI/doc-processing heavy; need async streaming + WebSockets.
- **Decision:** FastAPI + Pydantic v2 + SQLAlchemy 2 async + Alembic; API and workers share code.
- **Alternatives:** Node/NestJS; Django; Go.
- **Reasoning:** Best libraries for parsing/embeddings/AI SDKs; native OpenAPI; WS support.
- **Consequences:** Offload CPU-bound work to workers; careful async discipline; strict typing via mypy.

## D-03 Primary database: PostgreSQL — Accepted
- **Alternatives:** MySQL; MongoDB.
- **Reasoning:** Relational ownership model, RLS, pgvector, FTS, mature ops.
- **Consequences:** Single DB is the scaling/availability hinge; backups/PITR essential.

## D-04 Vector store: pgvector first, Qdrant as upgrade path — Accepted
- **Context:** Per-user, per-session small corpora; isolation critical; ops simplicity valued.
- **Decision:** pgvector in the primary Postgres behind a `VectorStore` interface.
- **Alternatives:** Qdrant (separate service); Pinecone/Weaviate (managed/other).
- **Reasoning:** Transactional consistency with ownership data, RLS-enforced isolation, one fewer service, tiny filtered sets make HNSW-filter recall issues moot (exact search fine). Migrate to Qdrant if chunk volume/QPS or hybrid features outgrow it.
- **Consequences:** Vector workload shares DB resources; HNSW index build/memory tuning; embedding dimension fixed per table.

## D-05 Background jobs: Dramatiq on Redis + `ingestion_jobs` table as source of truth — Accepted
- **Context:** Reliable ingestion with retries/failure states; cost-conscious infra.
- **Decision:** Dramatiq workers with Redis broker (AOF persistence). Job state/attempts/errors tracked in Postgres; periodic reaper re-enqueues stale jobs; steps idempotent.
- **Alternatives:** Celery (richer, heavier); Arq (async-native, less maintained); Procrastinate / Postgres-based queue (no Redis dependency for jobs; strong transactionality); RQ.
- **Reasoning:** Dramatiq is simple with built-in retries/backoff; DB table makes status queryable and recoverable regardless of broker loss. Redis already required.
- **Consequences:** Two sources of truth need reconciliation (reaper). If Redis durability proves troublesome, switch to Procrastinate (revisit in Phase 4).

## D-06 Redis for cache, rate limiting, pub/sub, broker — Accepted
- **Alternatives:** In-memory only; Memcached; Postgres-only.
- **Reasoning:** Single tool covers four needs; required for multi-node WS fan-out and rate limits.
- **Consequences:** Not a system of record; AOF on for broker; monitor memory.

## D-25 Open signup for internal use; same-origin web auth via Next.js proxy — Accepted
- **Context:** Owner approved open email/password signup for the current internal-use version (resolves OQ-7b). The web app and API run on different ports in development, and the refresh token must stay out of JavaScript.
- **Decision:** (1) Signup is open (no invite/allowlist, no email verification). (2) The browser only calls the web origin; Next.js rewrites `/api/*` to the API (`API_INTERNAL_URL`). The refresh token is an `HttpOnly; SameSite=Lax; Path=/api/v1/auth` cookie (`Secure` outside `APP_ENV=local`); the access token (15 min) lives in memory only. (3) Cookie-authenticated endpoints (`/auth/refresh`, `/auth/logout`) additionally reject an `Origin` not in `CORS_ORIGINS`. (4) CORS uses explicit origins with credentials, never `*`.
- **Alternatives:** Cross-origin fetch with `credentials: include` and CORS (needs SameSite=None or same-site tuning; larger CSRF surface); tokens in localStorage (rejected: XSS-exposed).
- **Reasoning:** Same-origin cookies remove CORS/third-party-cookie fragility and keep the long-lived credential unreadable by scripts. Production needs a reverse proxy that routes `/api/*` the same way.
- **Consequences:** Open signup + no email verification means account enumeration via the 409 on duplicate email is possible and there is no signup abuse protection until rate limiting is added. Refresh is strict single-use: concurrent refreshes with one token are treated as reuse and revoke the session, so clients must single-flight refresh. Access tokens remain valid up to 15 minutes after logout. Rewrite destination is fixed at build time for `next start`.

## D-26 File storage: local persistent server storage behind a `FileStorage` abstraction — Accepted (supersedes D-07)
- **Context:** The owner decided the initial/internal deployment will not use AWS S3, MinIO or any other object-storage service (no AWS knowledge/services required). In practice no anonymously pullable MinIO image was available (R-15), which prompted the review.
- **Decision:** Uploaded files are stored on persistent local server storage. All reads/writes/deletes go through a `FileStorage` interface (store, open/stream, delete, exists, by server-generated key) with a local-filesystem implementation. PostgreSQL stores metadata and ownership (`user_id`, `storage_key`, size, sha256, status), never file bytes. Object storage (S3-compatible or other) is a possible future implementation of the same interface, not a current requirement.
- **Logical layout (under a configured storage root, e.g. `/app-data` in containers):** `uploads/<user_id>/<kind>/<uuid>` where `<kind>` is `resumes` or `documents` (later `screenshots`). The file name on disk is a server-generated UUID with no client-supplied name or extension; the original filename lives only in the database as display metadata. The exact layout may be refined in Phase 3 for security/maintainability.
- **Persistence requirement:** Application containers/code are replaceable; uploaded user files must survive restarts and redeployments. In containerized deployment the storage root MUST be a persistent volume (bind mount or named volume) or equivalent persistent server storage. A container without such a mount would lose all uploads on redeploy. No hosting provider is selected by this decision.
- **Security requirements for the upload implementation (Phase 3):** (1) files are isolated per authenticated user identity; (2) the server never trusts a client-provided storage path, key or directory; (3) client file names are never used as filesystem paths; storage keys are server-generated and resolved paths are verified to stay inside the storage root (path-traversal protection); (4) uploads are validated (size, extension allow-list, MIME, magic bytes) before being stored, written to a temporary file and moved atomically; (5) every file read/delete enforces ownership (404 for other users' files); (6) files are never placed in a public static directory or served by a static file handler; downloads stream through an authenticated API endpoint; (7) restrictive filesystem permissions for the service account.
- **Alternatives considered:** S3/MinIO/other S3-compatible store (rejected for now: extra service/operational knowledge; MinIO image availability issue); storing file bytes in PostgreSQL (rejected: bloats DB/backups, though simple); a managed cloud file service (rejected: provider not selected).
- **Reasoning:** Simplest operation for an internal single-node deployment; the interface keeps business logic independent of the backend so a later move to object storage is an adapter change plus a data migration, not a rewrite.
- **Consequences:** (a) API and worker processes must see the same storage root (same host or shared mount); horizontal scale-out across hosts requires shared storage or the future object-storage implementation. (b) Backups of the storage volume must be taken and restored together with PostgreSQL (DB rows reference files). (c) Disk capacity monitoring and orphan-file cleanup (DB row without file, file without DB row) are required. (d) Encryption at rest relies on disk/volume-level encryption (see OQ-10 for application-level encryption). (e) Docker Compose no longer includes any object-storage service.

## D-27 Row-Level Security deferred; application-layer isolation for Phase 3 — Accepted, superseded by D-45
- **Status note:** This earlier deferral was superseded by the owner-approved Phase 3 security hardening in D-45. The original decision remains below for history.
- **Context:** D-14 calls for ownership checks plus Postgres RLS "where appropriate". RLS only protects when the API connects as a non-superuser, non-owner role (or tables use `FORCE ROW LEVEL SECURITY`) and every request sets `app.user_id` with `SET LOCAL`. Local dev and CI connect as the container superuser, and workers would need the same plumbing.
- **Decision:** Phase 3 enforces ownership in the application layer only: the file repository requires `user_id` on every read/delete (no unscoped query exists), identity comes only from `CurrentUser`, foreign access is a uniform 404, and two-user tests (with mutation checks) cover list/download/delete. RLS is deferred to a dedicated hardening step (before multi-table retrieval in Phase 5 at the latest, or Phase 13) when a restricted DB role and per-request `SET LOCAL` plumbing can be added and tested for API and workers together.
- **Alternatives:** Implement RLS now with a second DB role (rejected: widens Phase 3 into role/migration/connection plumbing); never use RLS (rejected: D-14 stays the target).
- **Consequences:** A coding mistake in a future query could bypass isolation until RLS exists; mitigated by the repository convention, mandatory two-user tests (TESTING_STRATEGY) and review.

## D-28 Upload pipeline and failure semantics (local storage) — Accepted
- **Decision:** Authenticate first, then stream the multipart body (early `Content-Length` limit plus byte counting) into a private temp file inside the storage root, validate extension/declared type/signature/size, move atomically to a server-generated key (`uploads/<user_id>/<resumes|documents>/<uuid hex>`), then insert the DB row. Client file names are sanitised for display only. Downloads stream through an authenticated endpoint with `attachment` disposition.
- **Failure handling:** (1) DB insert fails after the file is stored → the stored file is deleted and `500 save_failed` returned (a crash between the move and the insert can leave an unreferenced file; reconcile by comparing `uploads/` with `storage_key` values). (2) Record exists but the file is missing → `410 file_missing` with no path details; the record can still be deleted. (3) Delete order is file first, then row: if the file cannot be deleted nothing changes (`500 delete_failed`, retry); if the row delete fails after the file is gone the record remains, downloads return 410, and retrying the delete completes it. File-first was chosen over row-first so a failure never leaves hidden user data behind.
- **Consequences:** `tmp/*.part` files abandoned by a crash must be purged (`LocalFileStorage.purge_stale_temp`; scheduling is future work). Orphan reconciliation tooling is future work.

## D-29 Ingestion foundation: DB-backed jobs, extraction before chunking, sweep-based recovery — Accepted
- **Context:** Phase 4 (owner-scoped) adds background text extraction only. The queue is Redis/Dramatiq (D-05); PostgreSQL is the source of truth.
- **Decision:** (1) One `ingestion_jobs` row per file with statuses `pending/processing/completed/failed` (owner-approved names, replacing the earlier `queued/running/succeeded` wording). (2) The job row is created in the **same transaction** as the file record; the Dramatiq message is sent only **after commit**. A failed send leaves the job `pending`; it is never lost. (3) Workers claim with an atomic `UPDATE ... WHERE status='pending'`, so duplicate or concurrent deliveries are harmless; results are written only while the job is still `processing`, in one transaction that also upserts `extracted_texts` (idempotent, no duplicates). (4) Dramatiq retries are disabled (`max_retries=0`): the DB state plus the recovery sweep decide what is retried. (5) The recovery sweep (`python -m app.workers.recovery`, `--dry-run` to inspect) fails `processing` jobs stuck past `INGESTION_PROCESSING_TIMEOUT_SECONDS` once `INGESTION_MAX_ATTEMPTS` is exhausted, otherwise resets them to `pending`, and re-sends `pending` jobs older than `INGESTION_PENDING_REDISPATCH_SECONDS`. It is idempotent and deterministic (oldest first); scheduling it (cron/timer) is an operational step. (6) Extractors sit behind an `Extractor` interface keyed by the stored content type. (7) Extracted text lives in the database (`extracted_texts`), user-scoped, never returned by an API. (8) Files that predate Phase 4 receive a `pending` job via the migration.
- **Alternatives:** Dramatiq/Celery automatic retry with backoff (rejected for now: hides state and duplicates work); one row per attempt (rejected: more complexity than needed); storing extracted text as files (rejected: harder to query/clean up transactionally); PyMuPDF 2.x meta-package (rejected: pulls ONNX/layout extras; the 1.x core engine is pinned instead).
- **Consequences:** An unscheduled sweep means a lost queue message is only repaired when the sweep runs. Errors shown to users are fixed strings; diagnostics are in logs (IDs only). Chunking moves to Phase 5.

## D-30 Embedding model: `intfloat/multilingual-e5-large` run locally via fastembed (resolves OQ-3) — Accepted
- **Context:** Embeddings must cover English, Hindi and Telugu (OQ-3), must not make a paid external API mandatory, and user text is private (provider data-handling terms are an open risk). The project is internal-use.
- **Decision:** Default model `intfloat/multilingual-e5-large` (MIT licence, ~100 languages incl. Hindi and Telugu, 1024 dimensions, 512-token input window, needs `query:`/`passage:` prefixes), executed locally with **fastembed** (ONNX runtime, no PyTorch, no API key). fastembed is an **optional** dependency (`uv sync --extra embeddings`); it downloads the ~2.2 GB model from Hugging Face on first use into `EMBEDDING_CACHE_DIR`. All code depends only on the `EmbeddingProvider` interface (`model_id`, `dimension`, `embed_documents`, `embed_query`); a deterministic `FakeEmbeddingProvider` is the default **only in `APP_ENV=local` and in tests** (configuration rejects it elsewhere). Every stored vector records its `embedding_model`; the pgvector column is `vector(1024)`.
- **Evidence gathered:** model list from the fastembed library; a real run of the model on this machine (6 passages, 3 queries) ranked all three Python-experience passages (English, Hindi, Telugu) above the unrelated ones for English, Hindi **and** Telugu queries. This is a tiny smoke check, **not** a quality benchmark (PoC-4 stays open for real resume/job-description data).
- **Alternatives:** `jinaai/jina-embeddings-v3` (rejected: CC-BY-NC non-commercial licence); `paraphrase-multilingual-mpnet-base-v2` (50 languages, weaker Indic coverage) and `...MiniLM-L12-v2` (128-token window, too short); hosted APIs such as Gemini/OpenAI/Cohere embeddings (viable later behind the same interface; rejected as the default because they need credentials, cost money and send user text off-server); sentence-transformers/PyTorch (heavier install).
- **Consequences:** The worker host needs ~2.2 GB disk for the model and several GB RAM; CPU inference is slow (observed ~10 s per chunk batch element on a busy dev machine, unoptimised), so indexing is strictly a background job and large uploads will take a while. A model with a different dimension needs its own embeddings table (D-16) and a migration. Changing `EMBEDDING_MODEL` (same width) requires `python -m app.workers.reindex`; retrieval only compares vectors of the query's model, so nothing is mixed in the meantime (affected files are simply not searchable until re-embedded).

## D-31 Chunking and vector schema — Accepted
- **Chunking:** deterministic, character-based, sentence/line-aware, contiguous slices of the normalised extracted text (nothing rewritten or translated). Defaults `CHUNK_SIZE_CHARS=800`, `CHUNK_OVERLAP_CHARS=100` (bounds 200-4000; overlap at most half the size). Boundaries: line breaks and sentence ends (`. ! ? …` and the Devanagari danda `।`/`॥`), then word boundaries inside an over-long sentence, hard cut only for a single word longer than the chunk. Overlap consists of whole trailing sentences/lines up to the budget (a sentence longer than the overlap budget yields no overlap). 800 characters stay inside the model's 512-token window for English and, with margin, for Indic scripts (more tokens per character). Token-based sizing was rejected to avoid a tokenizer dependency.
- **Schema:** `chunks` (id, user_id, source_type, source_id, chunk_index, text, char_start, char_end, content_hash, created_at; unique per source+index) and `chunk_embeddings` (chunk_id, embedding_model, user_id, `embedding vector(1024)`; PK (chunk_id, embedding_model); cascade from chunks and users). Chunk text is stored with the chunk (extracted text remains the source for re-chunking without re-extraction). Separating chunks from vectors lets a model change replace vectors without touching the chunk model, and keeps vectors of different models distinguishable.
- **Indexes:** btree `(user_id, source_type, source_id)` on chunks and `(user_id, embedding_model)` on vectors. **No HNSW/IVFFlat index yet**: every search is constrained to one user's chunks (thousands at most) where an exact scan has perfect recall; an approximate index plus a restrictive filter can silently return too few rows. Revisit with PoC-8 if a user's corpus grows large (pgvector 0.8 iterative scans are the likely route).
- **Retrieval:** internal service `search_chunks(session, embedder, user_id, query, ...)`; `user_id` is enforced **in the SQL** on both tables together with the query model's id; cosine distance (`<=>`); limit validated 1..`RETRIEVAL_MAX_LIMIT` (20); query max 2000 characters; optional `source_type` / `source_ids` filters can only narrow the user's own data. **No public endpoint** exposes vector search.

## D-32 Embedding as a second database-backed job stage — Accepted
- **Context:** Embedding can fail independently of extraction (provider/model unavailable, slow) and must be retried without re-extracting.
- **Decision:** `ingestion_jobs` gains `stage` (`extract` | `embed`) and is unique per `(source_type, source_id, stage)`. Completing extraction creates (or resets) the `embed` job **in the same transaction** as the extracted text, and the worker dispatches it after commit. All existing machinery (atomic claim, conditional transitions, recovery sweep, retry endpoint, dispatch-failure recovery) applies to both stages unchanged. The embed stage: claim, chunk, skip if the stored chunks already match and have vectors for the current model (no repeated provider calls), otherwise embed **outside any DB transaction**, then in ONE transaction mark the job completed, verify the extracted text hash is unchanged, replace chunks + vectors and commit. A transient provider failure (`EmbeddingUnavailable`) returns the job to `pending` for an automatic retry via the sweep until `INGESTION_MAX_ATTEMPTS`, then `failed`; permanent errors fail immediately with a fixed code. Retry (`POST .../retry`) resets whichever stage failed; retrying `embed` never re-runs extraction. A file is searchable only when its `embed` job is `completed`.
- **Alternatives:** a separate `embedding_jobs` table (duplicates claim/recovery logic); embedding inside the extraction job (a provider failure would force re-extraction and widen the failure surface).
- **Consequences:** API files expose two status objects (`ingestion`, `indexing`); the UI shows Ready only when both are complete. `extracted_texts.text_sha256` was added so a slow embed worker cannot write chunks for outdated text. Existing completed files are backfilled with a pending `embed` job by the migration (picked up by the recovery sweep or `python -m app.workers.reindex`).

## D-33 LLM provider layer: port + router + breaker, core only, no real adapter yet (Phase 6) — Accepted
- **Context:** Phase 6 requires provider-neutral LLM access. OQ-4 (which providers/models are approved, who holds and pays for keys, acceptable retention/training terms) is **still open**, and RISKS section D says model names, pricing and data terms were never verified. When asked, the owner chose to build the provider-independent core and defer real adapters.
- **Decision:** `app/ai/` contains the `LLMProvider` port (`complete`, `stream_chat`; async), provider-neutral types, the error taxonomy (`RateLimited`, `Timeout`, `Unavailable`, `AuthError`, `ContentFiltered`, plus `InvalidSelection`), a registry/allowlist, `LLMRouter` (user selection, then fallback chain), a per-provider circuit breaker, usage records, a scripted `FakeLLMProvider`, and `GET /ai/options`. `app/ai/adapters/` is the only place provider SDKs may be imported (ruff TID251 + an AST test). **No real adapter ships**; `LLM_ENABLED_PROVIDERS` accepts only `fake`, and `fake` is rejected outside `APP_ENV=local`. Config is env-based (no `providers.yaml`, no new dependency).
- **Fallback rules:** fall back on `Timeout`, `Unavailable`, `RateLimited` and `AuthError` (a server-side credential fault, shown to users only as a generic "unavailable"). `ContentFiltered` and invalid selections never fall back (no shopping for a laxer filter). A stream falls back only before its first token; after tokens were delivered a failure is raised. Defaults: first-token timeout 4 s, stream idle timeout 15 s, request timeout 30 s. A provider with an open breaker is skipped; after the cooldown one half-open probe is allowed. Non-taxonomy provider exceptions are converted to `Unavailable` (no details leak).
- **Metering:** one `UsageRecord` per attempt (provider, model, token counts, latency, ok/error code, user id). The default sink logs identifiers and counts only, never prompt or answer text. Persistence is not added (no documented table); a DB sink can implement `UsageSink` later.
- **Not decided here:** the approved providers, models, keys and data terms (OQ-4); whether to use LiteLLM inside adapters (D-10 says evaluate; no adapter exists to evaluate it in). Tool calls are omitted from the port (no phase needs them yet).
- **Consequences:** the Phase 6 acceptance "same contract suite passes on all enabled adapters (recorded fixtures)" is met only for the fake adapter; the contract suite (`tests/ai_contract.py`) is ready for real adapters to join. Prompt construction (`PromptBuilder`) and `GenerationConfig` compilation remain Phase 7/8.

## D-34 Phase 7 owner decisions and the 7A compiler/PromptBuilder design — Accepted

Provider/model preferences are optional (omitted = server default chain; if given, validated against the server allowlist). **No composite-FK change to `resumes`/`documents`**: keep application-level ownership validation and revisit only if a concrete integrity gap is found. Sessions are hard-deleted (7B). `start`/`end` endpoints are deferred to the desktop/session phase. No inline upload in the wizard. Audit events deferred.

Matching is exact and case-sensitive; unknown values raise `InvalidPreference(field)` without echoing the value. `GET /ai/options` serves them (`languages`, `question_types`, `formats`, `lengths`, `tones`); `languages` now comes from the enum rather than from enabled providers, so it is non-empty even when no provider is enabled. Per-model language support stays on each model entry.
- **Compiler:** pure and deterministic (no DB, registry or LLM). Temperature per question type is a code constant (coding/system design/technical 0.2, auto/experience 0.3, how-do-you 0.4, behavioral/situational/introduction 0.5): starting values, unverified against any real model. Extra instructions are cleaned (NFC, control/bidi/zero-width/tag characters removed; ZWNJ/ZWJ kept because Hindi and Telugu need them) and **rejected, not truncated**, when over `EXTRA_INSTRUCTIONS_MAX_CHARS` (default 1000). Provider/model are shape-checked only; the allowlist check happens when a session is created (7B).
- **PromptBuilder:** all prompt prose lives in versioned files under `app/preferences/templates/v1/` (system, user, per-question-type, format, length, tone, language). `PROMPT_VERSION = "v1"`; a released version directory is immutable (a pinned fingerprint test fails on edits: add `v2` instead). The system message holds only trusted text. The job description, company, candidate material, earlier exchanges, the user's style preferences and the question are placed in the user message inside `<<<BEGIN UNTRUSTED:label>>>` / `<<<END UNTRUSTED:label>>>` blocks; `<<<` and `>>>` inside untrusted text are replaced by look-alike characters so a payload cannot forge a boundary, and substitution is single-pass so payloads are never re-expanded as placeholders. `PromptInputs` (question, company, JD, context passages, history) is the interface Phase 8 will fill; 7A never assembles it from retrieval and makes no LLM call.
- **Guards:** a test scans `app/` for inline prompt prose and for long string literals in `app/preferences/*.py`.
- **Assumptions to confirm:** the meaning of the three formats (`full_script` = spoken paragraphs; `script_bullets` = bullets that are full speakable sentences; `bullets` = short key phrases) and the template wording are my interpretation, not specified by the docs.
- **Consequences:** delimiting and the system-message hierarchy reduce, but do not eliminate, prompt-injection risk (R-9); behaviour against a real model is untested until an adapter exists (OQ-4, R-23).

## D-36 Job import (Phase 7C): SSRF-hardened, standard-library fetch, in-process limits — Accepted
- **Context:** `POST /sessions/job-import` lets the wizard pre-fill company/title/description from a public job link (D-20, accepted). It is the main SSRF exposure of Phase 7, so the controls are deliberately strict and independently tested. It stores nothing (no schema change, no migration), calls no LLM and never blocks manual entry.
- **Fetch policy (`app/jobs_import/ssrf.py`, `fetch.py`):** http/https only; ports 80 and 443 only; no credentials in the URL; no whitespace/control characters/backslashes; length <= 2048. The host is resolved and **every** returned address must be public (loopback, private, link-local incl. metadata 169.254.169.254, CGNAT, documentation/reserved/multicast, and IPv6 mapped/NAT64/6to4/Teredo/ULA/link-local ranges are blocked). The checks run on the resolved addresses, so decimal/hex/octal/short IP spellings and `localhost` variants are covered. The socket connects to the **validated IP** (never re-resolving: DNS rebinding cannot swap it) while TLS verifies the certificate for the hostname. Redirects are followed manually (max `JOB_IMPORT_MAX_REDIRECTS`, default 3) and **each hop is re-validated**. GET only, no cookies/credentials/referer, `Accept-Encoding: identity`, descriptive User-Agent, HTML/XHTML content types only, body capped (`JOB_IMPORT_MAX_BYTES`, default 1 MiB; over-limit fails rather than truncates), total deadline (`JOB_IMPORT_TIMEOUT_SECONDS`, default 8 s) enforced across connect, headers and every read (slow-drip responses are cut off).
- **Extraction (`extract.py`):** generic only (owner decision 12): schema.org JSON-LD `JobPosting` first, then Open Graph/`<title>`/`<main>`/meta-description heuristics. Output is cleaned plain text (markup removed, entities decoded, unsafe characters removed), company/title capped at 200 chars, description capped at the session JD limit. `succeeded` is only possible from structured JSON-LD data with all three fields; anything inferred from a generic page is at most `partial`; nothing found is `failed`.
- **Responses:** always `200` with `{status, company?, title?, description?, message}` and a **fixed** message. Blocked address, DNS failure, connection error, TLS error, timeout, redirect problems and HTTP errors all return the **same** message, so the endpoint is not an oracle for probing internal hosts or ports. Only an invalid link, a non-HTML target, an oversized page and "no job information" have their own (harmless) messages. URLs, page content and provider/exception text are never logged or returned; logs carry the user id, outcome and an internal reason code only.
- **Limits and infrastructure:** authenticated; per-user sliding-window rate limit (`JOB_IMPORT_RATE_LIMIT_PER_MINUTE`, default 10; blocked/invalid attempts count, so probing is throttled) and a per-process concurrency cap (`JOB_IMPORT_MAX_CONCURRENT`, default 4), both **in-process** (no Redis), answered with `429` and `Retry-After`. The fetcher uses `http.client` from the standard library: no new dependency (`httpx` stays dev-only) and no new infrastructure. These two choices differ from the Phase 7 plan (which suggested `httpx` and a Redis limiter) in favour of the owner's "keep infrastructure simple" instruction.
- **Wiring:** `app.state.job_importer` is built at startup with the strict default `UrlPolicy`; tests assert this. A looser policy exists only as a test helper (`tests/job_server.py`) so the suite can use a local server; it is not reachable from configuration. `POST /sessions/job-import` is registered before `/sessions/{session_id}`.
- **robots.txt / site terms:** not enforced in this version (a single user-initiated fetch of a user-supplied public URL with a descriptive User-Agent; no crawling). The architecture says "where applicable"; this is recorded as an open risk (R-29) to revisit before any external or commercial use. No site-specific adapters, no headless browser.
- **Session creation:** `job_url` on `POST /sessions` is still only stored, never fetched (tested). Using the import result is a UI step for Phase 7D.
- **Consequences:** residual risks are listed in R-28 to R-31 (DNS lookups are not individually time-bounded, per-process limits, robots/ToS, untrusted page text).

## D-39 Typed Q&A API and streaming layer (Phase 8B) and the material-deletion rule — Accepted
- **Material deletion / readiness rule (owner clarification, applied to 8A):** if ANY material a session explicitly selected is deleted or is no longer Ready, the question is refused with `409 materials_not_ready`; the context is never silently reduced. This supersedes the earlier "a deleted document is simply absent" reading in D-38. Implementation: the selection is the session's `materials_snapshot` (what the user chose, refreshed whenever the session's materials are edited); a snapshot document whose link is gone (the document was deleted), a resume that is deleted, and any selected resume/document whose extraction or indexing is not `completed` all refuse. The user changes the selection explicitly by editing the session (`PATCH`), after which questions work again. Unselected documents never matter.
- **Endpoints (only these three, owner decision 9):** `POST /api/v1/sessions/{id}/questions`, `GET /api/v1/sessions/{id}/questions`, `GET /api/v1/sessions/{id}/answers/{answer_id}`. Contract in docs/API.md. All require authentication; the user's identity comes only from the token.
- **Streaming contract:** `POST` requires `Accept: text/event-stream` (checked after authentication and before the body is validated); anything else is `406 not_acceptable` with nothing persisted and no limit consumed. The response IS the stream (`200`, `text/event-stream`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`). Frames are `event: <name>\ndata: <one-line JSON>\n\n`; JSON escapes every newline so answer text cannot split or forge a frame. Order: `question.created` -> `retrieval.done` -> `answer.started` -> `answer.delta`* -> `answer.done`, or `... -> answer.error` (never both). `answer.done` carries `metrics{retrieval_ms, first_token_ms, total_ms}`, `provider`, `model`, `fallback_used` and token counts. The first event is read BEFORE the response starts, so refusals (`404`, `409 session_not_ready`, `409 materials_not_ready`, `422`, `429`) are ordinary JSON errors with the right status and never SSE.
- **Failure handling:** provider, retrieval and orchestration failures become `answer.error` events with fixed codes/messages (`llm_*` taxonomy, `retrieval_failed`, `empty_answer`, `internal_error`) and a persisted `error` answer (partial text kept); an unexpected failure inside the stream becomes a generic `answer.error`. Provider internals, prompt content, credentials and stack traces never reach SSE, the database or logs.
- **Disconnect handling:** `SseResponse` always runs a cleanup when the response ends, however it ends: it closes the answer generator (which records a `cancelled` answer with the partial text and, through `aclosing`, closes the router and provider streams) and releases the user's concurrency slot, outside the cancelled scope. A `finished` flag ensures a completed answer is never downgraded to `cancelled`, and `finish_answer` itself refuses to rewrite an answer that is already `complete` (`status != 'complete'` in the UPDATE), so a late cancellation or error can never downgrade it even if the flag were wrong.
- **Limits (in-process, no Redis; same trade-off as R-30):** per user, `QA_RATE_LIMIT_PER_MINUTE` (default 20; every authenticated attempt that passes the 406 check counts, including ones later refused) and `QA_MAX_CONCURRENT_GENERATIONS` (default 2). Refusals are `429 rate_limited` / `429 too_many_generations` with `Retry-After`. The limiter is the existing `SlidingWindowLimiter`. Slots are released on success, failure, refusal and disconnect.
- **Time budget and stale rows:** `QA_REQUEST_TIMEOUT_SECONDS` (default 120) is the total budget of one generation, checked as events arrive (a stalled provider is also bounded by the router's first-token/idle timeouts); exceeding it fails the answer with `llm_timeout`. A `streaming` answer older than that budget can only be an orphan, so the read endpoints treat it as `error` (`error_code generation_interrupted`) and persist that, scoped by user AND session, with no scheduler.
- **History reads:** `GET questions` lists the session's questions oldest first with their answers (cursor pagination on `(detected_at, id)`, `limit` 1-100, default 20; `confidence` is always null for typed questions). `GET answers/{id}` returns one answer with its metrics. Both expose only user-facing fields (never the prompt, generation config, retrieved chunk ids or user/session ids). The session must belong to the user first; unknown and foreign sessions, and unknown or foreign answers, return indistinguishable 404s. Every query filters on both `user_id` and `session_id` (tests use mixed-owner rows so each filter is individually necessary).
- **Wiring:** `app.state.question_answerer` (lazy query-embedding model through the existing cached factory, never loaded at startup; own short DB sessions from the app sessionmaker) and `app.state.question_limits`, created in the app lifespan. No schema change (no migration in 8B).
- **Not built (owner boundaries):** the frontend session page (8C), regenerate, cancel endpoint, export, `/me/history`, aggregated metrics, real provider adapters, query rewriting/MMR/reranking/hybrid search.
- **Consequences:** R-36 is partly verified (see RISKS); R-38 to R-40 below.

Each step ends with a report; the next one starts only on explicit instruction. No migration in any step.
- **Owner decisions:**
  1. **Resume = Option A:** generation is detached from the socket, events go into a bounded in-memory buffer, and a dropped socket does NOT cancel immediately. A reconnect inside a 30 s grace period resumes with `resume_from_seq`; after the grace period the generation is cancelled and the partial answer is persisted `cancelled`. (Built in 9B/9C; 9A only fixes the contract and the field.)
  2. **Contract changes approved:** `POST /auth/ws-ticket`; new server events `question.created` and `answer.cancelled`; the WS `answer.done` payload is identical to the SSE one; the reconnect field is `resume_from_seq`.
  3. **Tickets:** stored in **Redis** in production; the store has no in-memory production implementation (tests drive the same Redis store class through a fake Redis client). A ticket is 32 random bytes (urlsafe), only its SHA-256 is stored (`ws_ticket:<hash>` -> user id and session id, `SET NX EX`), redeemed atomically and once (`GETDEL`), short-lived (default 30 s), bound to the user AND the session, and never logged.
  4. **Generated types:** an in-repository generator (`app/realtime/codegen.py`, `python -m app.realtime.codegen`, no new dependency). Pydantic models -> JSON Schema -> TypeScript. Output is committed under `packages/protocol/`; a test regenerates it and fails on drift.
  5. **Web page stays on SSE.** WebSocket is a backend realtime gateway for future consumers (Phase 10 desktop). `apps/web` is not touched.
  6. **A new question during an active generation** is rejected with a non-fatal `error` (`generation_in_progress`); the active generation is never cancelled implicitly. (Built in 9B.)
  7. **Scale defaults approved, all configurable:** ticket TTL 30 s, ticket requests 30/min/user, heartbeat 20 s, idle timeout 45 s, max frame 16 KiB, 10 messages/s, 3 connections per user, 200 total, resume buffer 2000 events, resume grace 30 s. (OQ-2 stays open as an input to later tuning.) The buffer and grace settings are added in the step that uses them (9B/9C), so 9A has no unused configuration.
  8. **Doc housekeeping allowed; no status promotions.** Stale status text may be corrected, but no phase is marked accepted/owner-approved without explicit owner approval. Nothing is committed or pushed by the assistant.
- **Protocol (9A):** JSON text frames only (a binary frame closes the socket with 1003; audio is out of scope). Envelope `{type, id, seq, ts, payload}`; `ts` is epoch milliseconds; server `id` is a random hex message id. Client envelopes carry `type`, optional correlation `id` (<= 64 chars) and `payload`; unknown envelope or payload fields are rejected. **Control events** (`session.ready`, `pong`, `error`) carry `seq: 0` and are never buffered or replayed; **sequenced events** (the Q&A events, from 9B) carry a per-(user, session) channel `seq >= 1`. `protocol_version` (integer, currently `1`) and the optional `resume_from_seq` live in the `client.hello` payload. `audio_params` is optional and absent until audio exists. In 9A `resume_seq` is always `0`, and a hello with `resume_from_seq > 0` gets the non-fatal `error resume_unavailable` (the same answer 9C gives when the buffer no longer holds the sequence); `question.submit` and `answer.cancel` are valid envelopes that get a non-fatal `error not_available` until 9B.
- **Handshake (9A):** `GET /api/v1/ws/sessions/{session_id}?ticket=...`. Checks run before the socket is accepted and every failure is the same bare handshake refusal (HTTP 403, no body, no reason): `Origin` present and not in `CORS_ORIGINS` (browsers only; non-browser clients send none, as for `require_trusted_origin`), missing/garbage/expired/reused ticket, ticket bound to a different session than the path (checked before any database access, so it cannot probe ownership), user missing or not active, session not owned by the ticket's user, malformed session id. After accept: `session.ready {session_id, server_time, resume_seq, protocol_version, limits}`; the client's first message must be `client.hello` within the hello timeout (default 10 s). Identity comes only from the ticket; no client message can carry a user or session id. The server-side log carries a fixed reason code and ids, never the ticket. `POST /auth/ws-ticket` requires a Bearer token, is rate limited first (every attempt counts, 404s included), then checks ownership with the same `404 session_not_found` as an unknown session.
- **Connection rules (9A):** one socket per (user, session): a newer connection supersedes the older one (closed 4001). Per-user (3) and total (200) caps are checked after authentication, so they leak nothing: the socket is accepted, a fatal `error too_many_connections` is sent and it is closed 4429. Heartbeat: the client pings about every 20 s, the server answers `pong`; any received frame resets the idle clock; 45 s of silence closes 4002. Frames larger than the limit close 1009; more than the allowed messages per second close 4005; malformed/unknown/invalid messages get a non-fatal `error` (`invalid_message`, `unknown_message_type`), five of them close 4003; a wrong first message or a second `client.hello` is `protocol_error` (fatal, 4003); an unsupported `protocol_version` is fatal, 4004. Close codes are documented in API.md section 8.
- **Ticket and log hygiene:** the ticket is in the URL because browsers cannot set WebSocket headers (it is single-use and expires in seconds). Uvicorn writes the request target, including the query string, to its access/error logs; `app/core/logging.py` therefore installs a redaction filter (`ticket=...` -> `ticket=[redacted]`) on the uvicorn and websocket-library loggers and on the application handler. The frame limit is enforced by the gateway; the transport-level maximum (`--ws-max-size`) should also be lowered in deployment (documented in the README run command).
- **Limits of 9A (see RISKS R-44 to R-47):** the connection lives as long as the peer pings; it is not bound to the 15-minute access token and a user disabled or a session deleted after the handshake is only noticed when the next action (9B) re-validates; limits are per process (R-14, R-38); WebSocket and SSE share one Q&A core, so no Q&A logic is duplicated.
- **Not Phase 9:** audio, transcripts, `question.detected/possible`, `force_answer`, `dismiss`, screenshots, `answer.regenerate`, `prefs.update`, `provider.fallback`, export, metrics, `/me/history`, the desktop client, Redis-backed shared limiters, multi-node WS scaling.

## D-42 Phase 9B design: typed Q&A over WebSocket, cancel and backpressure — Accepted (the owner approved starting 9B and accepted it)
- **One core, two transports.** `question.submit` calls `QuestionAnswerer.ask` unchanged and `app/realtime/adapter.py` maps the six `QaEvent` types to protocol envelopes (payloads identical to the SSE frames, parity-tested). `QuestionLimits` (rate and concurrency, shared with SSE) is reused; the slot is released exactly once however the generation ends.
- **Per-connection channel.** `app/realtime/channel.py`: a sequence counter for the Q&A events (control events are `seq` 0) and ONE bounded outbound queue drained by ONE writer task, so there is a single writer per socket and generation is never blocked by a slow client. Overflow of the queue (`WS_SEND_QUEUE_EVENTS`, default 1000) or a single send that exceeds `WS_SEND_TIMEOUT_SECONDS` (default 10) makes the client a slow consumer: the socket is closed `4010` (`slow_consumer`), the generation is cancelled and cleaned up. The two settings are new in 9B (they belong to the backpressure design; the resume buffer and grace settings stay in 9C).
- **Generation task.** `app/realtime/generation.py`: at most one active generation per socket (a second `question.submit` is a non-fatal `error generation_in_progress`, decision 6); the generation runs as its own task so the receive loop keeps serving pings and `answer.cancel`. Cancellation (`answer.cancel` or a closing socket) cancels that task; `ask` already records a `cancelled` answer with the partial text and never downgrades a completed one; the provider stream is closed, the slot released and the registry/queue freed in a `finally` that runs shielded.
- **Errors.** Pre-stream refusals map `AppError` codes to non-fatal control `error` events with fixed, per-code messages (nothing from the request or an exception is ever interpolated). `answer.cancel` for anything that is not the running generation is one indistinguishable `nothing_to_cancel` (no ownership oracle). The user's active status is re-checked on every `question.submit` (R-44 mitigation); a disabled user gets a fatal `account_inactive` and close `1008`.
- **Scope kept out of 9B:** detaching generation from the socket, the grace period, buffer retention and `resume_from_seq` replay, the load smoke (all 9C); the web page stays on SSE.
- **Superseded in part by D-43 (Phase 9C):** the per-connection sequence counter, the per-connection outbound queue for sequenced events and the generation that dies with the socket are replaced by the per-(user, session) channel, the retained buffer and the detached generation. Everything else in this entry stands: the shared `ask` core and the SSE payload parity, one generation at a time (now per channel), the `answer.cancel` semantics and `nothing_to_cancel`, the error codes and fixed messages, the per-question account re-check, and the 4010 slow-consumer close (which now detaches instead of cancelling).

## D-43 Phase 9C design: detached generation, resume and Phase 9 closure — Accepted (owner-approved starting 9C; 9C and Phase 9 accepted by the owner)
- **Per-(user, session) channel (`app/realtime/session_channel.py`).** The sequence counter, the bounded retained buffer of sequenced events (`WS_RESUME_BUFFER_EVENTS`, default 2000, plus an internal 2 MiB byte budget so a few huge deltas cannot hold unbounded memory) and the one active `Generation` now live in a channel keyed by `(user_id, session_id)` taken from the ticket. A connection attaches at `client.hello` and detaches when its socket ends; identity checks make a superseded socket's late detach a no-op. This replaces the 9B per-connection counter and queue for sequenced events.
- **Detached generation (owner decision 1, Option A).** A detaching socket does not cancel: the generation continues and writes into the buffer for `WS_RESUME_GRACE_SECONDS` (default 30). Expiry cancels it (`ask` stores `cancelled` with the partial text, the slot is released) and frees the buffer. Also at shutdown, and by a cap: more than `WS_MAX_TOTAL_CONNECTIONS` detached channels evicts the oldest-detached first, so detached state cannot grow without bound across reconnects. A channel that never carried an event is dropped at detach. No new cap setting.
- **Replay.** `resume_from_seq` N replays the retained events with `seq > N` in order, exactly as first sent, in the same synchronous step that attaches the socket so no live event can overtake the replay; N equal to the last `seq` or absent/0 replays nothing; an expired channel, evicted events or an N above the last `seq` answer the non-fatal `resume_unavailable` (no replay). Backpressure is a per-connection read cursor on the shared buffer: a cursor that falls behind the oldest retained event is a slow consumer (4010); control messages keep a small bounded queue (`WS_SEND_QUEUE_EVENTS`). A slow-consumer close detaches rather than cancels.
- **Database stays the source of truth (cancel versus the final commit).** When a user cancel interrupts a generation, the terminal event is derived from the stored answer row, not from the interrupted task: `cancelled` (or a row still `streaming`, read as cancelled) sends `answer.cancelled`; `complete` (the cancel lost the race with the final commit; `finish_answer` already refuses to downgrade it) sends `answer.done` rebuilt from the row; `error` sends `answer.error` with the stored code. This closes the R-49-era edge found in 9B.
- **Isolation.** The channel registry is keyed only by identity from the ticket; resume reads only that channel; the handshake still checks ticket, session ownership and an active account, so a disabled user or a deleted session cannot reattach, and the per-question account re-check (D-42) still applies to every question. Cancel works on the channel's own generation only, from any socket of that (user, session).
- **Contract additions (additive):** `session.ready.limits.resume_grace_seconds` and `resume_buffer_events`; settings `WS_RESUME_BUFFER_EVENTS` and `WS_RESUME_GRACE_SECONDS` (both approved defaults in D-41 decision 7). `WS_SEND_QUEUE_EVENTS` now bounds control messages only.
- **Phase 9 closure:** load smoke (N concurrent real connections, default 50), live reconnect/resume tests on a real socket, mutation checks, full regression; Phase 9 exits when the owner accepts 9C.
- **Still out of scope:** audio, transcripts, a Redis-backed channel/buffer or multi-worker resume (R-46), screenshots, `answer.regenerate`, the desktop client, any web-page change (the web stays on SSE).

## D-48 Post-generation citation-integrity check (record-and-observe) — Accepted (owner-approved Issue 2)
- **Context:** Prompt v2 labels each candidate excerpt `[E<n>]` and asks the model to cite supporting excerpts on an `Evidence (not spoken):` line. Nothing verified afterwards that a cited ID refers to evidence supplied for that request.
- **Decision:** `PromptBuilder.build` exposes `BuiltPrompt.evidence`, the tags it actually rendered (number plus long-form metadata), so numbering is decided in one place. After streaming ends, `QuestionAnswerer` runs the pure `app.qa.grounding.check_citations` once over the complete accumulated text and records a content-free `grounding_check` (migration 0009), a counts-only log line and the `interview_answer_grounding_checks{status}` metric. Strict grammar: `[E<n>]` (1..999999, no leading zero) or the long form with metadata matching the rendered entry; look-alikes, comma lists, unclosed or otherwise malformed tags are counted as malformed; adjacent `[E1][E2]` are two valid tags; an ID that was not rendered, or a long-form tag whose metadata differs, is `unknown`. Invisible characters are removed before matching.
- **Record-and-observe only:** the check never delays, buffers, alters, blocks, regenerates or retracts streamed text, never changes the answer status (a bad citation still ends `complete`), and any error inside it is isolated and recorded as `check_error`. Cancelled and errored answers are not checked. No API, SSE or WebSocket contract changes and no client signal (a client-facing signal would be a separate decision).
- **What it does NOT establish:** this is a citation-integrity check, not proof of grounding. A valid citation does not show the cited excerpt supports the sentence; an uncited or fabricated claim passes unnoticed (`no_citations` is informational, because rule 3 allows omitting the evidence line); bare mentions without brackets are not tags; paraphrase and semantic support are not checked; Hindi/Telugu answers are checked for tag structure only; recorded ID lists are capped at 50. Uncited-claim detection, semantic claim verification and live-model evaluation remain out of scope and R-37/OQ-4 stay open.
- **Dependency:** relies on the evidence-tag neutralisation of untrusted channels (Issue 1) so only builder-made tags exist in the prompt.
- **Migration:** `0009_answer_grounding_check` (additive, nullable `generated_answers.grounding_check jsonb` plus an object-only CHECK). See `docs/DATABASE.md`.

### D-52 addendum — "Open web app" recommendation (Proposed; not implemented; no Electron capability changed)
- **Smallest safe approach:** one purpose-specific IPC `app:open-web-app` with **no arguments**. The main process builds the URL itself from a new `webAppUrl` setting plus the fixed path `/sessions/new`; the renderer never supplies a URL. The setting is validated exactly like the backend URL: `https:` only, or `http:` only for loopback; no credentials, query or fragment; default `http://localhost:3000` only when the backend URL is loopback, otherwise unset (the button is hidden and the existing copy-link fallback stays). The URL is re-validated at the moment of opening.
- **Does it need** (a) a fixed configured web URL — **yes** (the desktop cannot know the web app's address; production address is a Phase 14 fact); (b) a narrow `shell.openExternal` allow-list — **yes**, but not a list: a single computed URL, `shell.openExternal` referenced from exactly one module (source-guard test), no other caller; (c) validation that only approved HTTP/HTTPS URLs can be opened — **yes**: parse with `URL`, protocol allow-list, host must equal the configured host, reject everything else (`file:`, `javascript:`, custom schemes, other hosts).
