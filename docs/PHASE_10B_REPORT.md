## 2. Security changes and rationale

- **`style-src 'self'`**: removes the ability for injected markup to apply arbitrary inline styles (CSS-based exfiltration/UI redress). Phase 10A showed the app needs no inline styles.
- **`form-action 'none'`**: the UI has no real form submission (React handlers call the bridge), so a form post to any target is now blocked. Verified: login still works.
- **Fuses** (details in §4): block the packaged binary from being turned into a Node interpreter or having an inspector attached through environment variables/flags, and make a modified `app.asar` crash instead of running.
- **IPC messages**: validation errors no longer mislabel the cause; the messages are fixed strings and echo no input.

## 3. CSP verification (packaged build, real backend)

- Method: CDP against the packaged exe; a `securitypolicyviolation`/`error`/`unhandledrejection` collector installed with `Page.addScriptToEvaluateOnNewDocument` before a fresh load.
- **0 violations, 0 exceptions** on load and across Login → Sessions → Assistant (a streamed question) → History → Settings → back, and after an app restart.
- Page fully styled: 168 CSS rules (identical to the 10A throwaway result).
- Positive control: a `<style>` element injected at runtime **is blocked** (`style-src-elem inline` recorded), so the detector works.
- Built `out/renderer/index.html` contains the strict policy. Dev server: the policy has `'unsafe-inline'` only for `style-src` (169 rules, 1 injected style tag, verified); this exists only in `electron-vite dev`.
- `connect-src 'none'` unchanged; the renderer still cannot fetch.

## 4. Electron fuse / security evaluation

Fuse state was read back from the packaged binary after build. Behavioural tests are stated where they were done.

| Fuse / setting | Protects against | Decision | Evidence |
|---|---|---|---|
| `RunAsNode` = off | A local process running the app binary as a generic Node runtime with `ELECTRON_RUN_AS_NODE` (code execution with the app's identity; the 10A-style hijack) | **Enabled.** The app uses no `child_process`/`fork` (grep). | Launching the packaged exe with `ELECTRON_RUN_AS_NODE=1 -e ...` started the GUI app instead of running the script. |
| `EnableNodeOptionsEnvironmentVariable` = off | Injecting `--require`/inspector flags through `NODE_OPTIONS` | **Enabled** | Fuse read back. Behaviour **not proven**: see below. |
| `EnableNodeCliInspectArguments` = off | Attaching the Node inspector with `--inspect` | **Enabled** | Fuse read back. Behaviour **not proven**: the packaged app showed no inspector listener, but my unfused control also showed none, so the probe could not discriminate. |
| `EnableCookieEncryption` = on | Plaintext cookie store on disk | **Enabled.** The app sets no cookies; no data migration risk. | Fuse read back; app works. |
| `EnableEmbeddedAsarIntegrityValidation` = on | Tampered `app.asar` running silently | **Enabled** (Windows supported, electron ≥ 30) | Flipping one byte in the asar header or in file content in a scratch copy made the app exit at startup (exit code `-2147483645`); an untouched copy ran normally. Note: this detects asar modification, not replacement of the executable itself (that is what code signing is for). |
| `OnlyLoadAppFromAsar` = on | Loading unvalidated code from an `app/` folder next to the asar | **Enabled** (`asar: true`) | App runs from the packaged build. |
| `GrantFileProtocolExtraPrivileges` = off | Extra powers granted to `file://` pages | **Rejected — breaks the app.** The renderer is loaded with `loadFile` (`file://`). With the fuse off, the packaged app showed the "could not start" dialog in 4 of 4 launches (without the fuse: 4 of 4 launches started). **Kept at default (enabled).** | Bisected by toggling only this fuse on the same build. Prerequisite for revisiting it: serve the renderer from a custom protocol instead of `file://` (a main-process change plus a new trusted-renderer check; needs its own approval). |
| `LoadBrowserProcessSpecificV8Snapshot` | Not a security control for this app | Not changed | — |

Notes:
- `--remote-debugging-port` is a Chromium switch, **not covered by any fuse**; the packaged app still honours it (this is how it was driven for testing). Anyone who can launch the exe as the same Windows user can already read that user's `%APPDATA%` data, so this is low impact, but it is not closed. Closing it would need an explicit check in the main process (not done; no speculative change).
- Existing settings unchanged and re-confirmed in code: `contextIsolation`, `sandbox`, `nodeIntegration: false`, `webviewTag: false`, `webSecurity`, navigation/`window.open`/permission handlers, per-handler sender validation.

## 5. Dependency advisory analysis

All **six** findings are one advisory propagated up a chain: **GHSA-g3hv-75wg-m249** (`minimatch` >=7.0.0 <11.0.1, "potential denial of service via globparts amplification", CWE-405, severity **moderate**; the advisory gives no CVSS score).

| Package (audit entry) | Affected range | Role |
|---|---|---|
| `minimatch` (10.2.6 under `app-builder-lib`, 9.0.9 under `@electron/universal`) | 7.0.0–11.0.0 | the vulnerable code |
| `@electron/universal`, `app-builder-lib`, `dmg-builder`, `electron-builder-squirrel-windows`, `electron-builder` | inherit the finding | reported only because they depend on it |

- **Runtime vs tooling:** development/build tooling only. `npm audit --omit=dev` reports **0** vulnerabilities; the packaged app does not include these modules. Exposure: a build with attacker-controlled glob patterns; electron-builder's patterns come from this repo's own `package.json`.
- **Available "fix":** `npm audit fix --force` proposes `electron-builder@24.13.3`, a major **downgrade** from the current latest (26.18.0). Rejected.
- **Override experiment:** forcing `minimatch@11` for `app-builder-lib` and `@electron/universal` clears the audit in the lockfile. However `npm ls` showed the override cascades into `glob@7.2.3` and `dir-compare@4.2.0`, which depend on the minimatch 3 API (`^3.x`). A global override has the same problem. That risks breaking the build in ways the existing tests do not cover, so it was **reverted** (`package.json`/lockfile restored; `npm install` re-run; audit unchanged at 6 moderate).
- **Action taken:** none applied. **Recommendation:** accept as a documented, non-runtime risk and re-run `npm audit` after each electron-builder release; a clean upstream bump (electron-builder/app-builder-lib moving to minimatch ≥ 11.0.1) is the safe fix. Compatibility risk of the manual override: medium (cross-major API change inside the tool's dependency subtree).

## 6. Window-minimization investigation

Observed in 10A: the window was sometimes found minimized when always-on-top was off. **Result: not reproduced; recorded as observed but unconfirmed. No speculative code was changed.**

What was checked:
- **Creation/state restoration:** the window is created `show: false`, then shown on `ready-to-show`; persisted state is only `alwaysOnTop`, `opacity`, `expanded`, `backendBaseUrl` (settings file). Window position, minimized or maximized state is **not persisted or restored**, so a minimized state cannot come back from disk.
- **Event handling:** there is no `blur`, `hide`, `minimize` or visibility handler in the main process. The only code that minimizes is the `app:minimize` IPC, reachable only from the title-bar "−" button.
- **Controlled test** (a standalone Electron script with the app's window options, run for always-on-top on and off): shown → `minimize()` → `show()` (what the tray "Show Assistant"/double-click calls) → `focus()` → `hide()` (close-to-tray) → `show()` → toggle always-on-top → change opacity and size. In every step the window ended up visible and not minimized; `show()` restores a minimized window in Electron 45 on Windows, and toggling always-on-top, opacity or size never minimized it. No difference between always-on-top on and off.
- **Candidate explanations that are not defects in the main process (unverified):** (a) the "−" button was mislabelled "Minimize to tray" although it minimizes to the taskbar, so a tester could minimize by clicking it and expect it to be in the tray (label fixed, see §1 item 7); (b) the 10A test harness or an OS action (for example Show Desktop) acting on the window while it was not always-on-top. Neither could be confirmed.
- **Please watch for it** during hands-on testing with always-on-top off and note what preceded it.

## 10. Auto-update recommendation

Proposal only, not implemented; see [DESKTOP_RELEASE.md](./DESKTOP_RELEASE.md#b-auto-update-architecture). Order: signed installer with published hashes (manual update) first; then `electron-updater` over a dedicated HTTPS static host with signature verification, staged rollout and a tested rejection of unsigned or tampered updates. An update channel is an RCE path, so it requires signing first.

7. `GET /metrics` is unauthenticated (backend, pre-existing).
8. No automated packaged-app smoke in CI; the CDP scripts used here were kept outside the repository.
9. Environment: if `ELECTRON_RUN_AS_NODE=1` is set in a terminal (VS Code-hosted shells), Electron behaves like Node (documented in `DESKTOP_WINDOWS.md`).
