# API Contract

**Implemented so far (Phases 2–9; endpoints marked ✅ in each section):** `GET /health`, `GET /ready`, the auth endpoints, resume/document endpoints, `/sessions` CRUD and `/sessions/job-import`, `/ai/options`, typed Q&A endpoints (SSE + history), and the WebSocket handshake, Q&A, cancel, and resume flow. Everything else is a future contract.

Base: `/api/v1`. JSON unless noted. Auth = `Authorization: Bearer <access_token>` (web may use refresh cookie for `/auth/refresh`). Errors: `{ "error": { "code": "string", "message": "string", "details": {}, "request_id": "..." } }`. Cross-user resource access returns `404`. Lists use cursor pagination: `?limit=&cursor=` → `{ items: [], next_cursor }`. State-changing endpoints may accept `Idempotency-Key`. Rate limits return `429` with `Retry-After`.

Common statuses: 400 validation, 401 unauthenticated, 404 not found/not yours, 409 conflict, 413 too large, 415 unsupported type, 422 schema error, 429 rate limited.

## 2. Resumes ✅ (Phase 3)
All endpoints require `Authorization: Bearer <access_token>`. Another user's resource is always `404 not_found` (indistinguishable from a missing one). Responses never include storage keys, hashes or filesystem paths.

| Method | Path | Purpose | Request → Response |
|---|---|---|---|
| POST ✅ | /resumes | Upload a resume | `multipart/form-data` field `file` (PDF or DOCX, max 10 MB by default). → `201 {id, filename, content_type, size_bytes, created_at, ingestion, indexing}` (the two stage objects are described below; a new upload starts `pending`). Errors: `415 unsupported_file_type`, `413 file_too_large`, `422 invalid_file_content` / `empty_file` / `file_required`. |
| GET ✅ | /resumes | List own resumes (newest first) | `?limit=` (1–200, default 100) → `{items:[{id, filename, content_type, size_bytes, created_at, ingestion, indexing}]}`; a file is **ready** only when `ingestion.status` and `indexing.status` are both `completed`. Cursor pagination is deferred. |
| GET ✅ | /resumes/{id}/file | Download original | Ownership-checked and streamed by the API from `FileStorage` (no public/static or presigned URL). `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`. `410 file_missing` if the record exists but the stored file is gone. |
| DELETE ✅ | /resumes/{id} | Delete resume record and stored file | → `204`. `500 delete_failed` is retryable (see DECISIONS D-28). |
| GET ✅ | /resumes/{id} | File details with ingestion status | → `{id, filename, content_type, size_bytes, created_at, ingestion, indexing}` |
| POST ✅ | /resumes/{id}/retry | Re-queue a **failed** ingestion | → `202` + same body; `409 not_retryable` unless the status is `failed` (so double submission cannot duplicate processing) |

**`indexing` object (Phase 5):** same shape as `ingestion`, describing the chunking + embedding stage. A file is ready for search only when `ingestion.status` and `indexing.status` are both `completed`. Additional `error_code`s: `embedding_unavailable` (transient; retried automatically, then `failed`), `embedding_failed`, `embedding_dimension_mismatch`, `provider_not_installed`, `unknown_embedding_model`, `text_missing`, `no_chunks`. `POST .../retry` resets whichever stage failed (retrying `indexing` does not re-run extraction). **There is no public search/retrieval endpoint**; retrieval is an internal service for future phases and never accepts a client-supplied user id.

**`ingestion` object (Phase 4, also on list/upload responses):** `{status: pending|processing|completed|failed, error_code, error_message, updated_at}`. `completed` means the text was extracted and stored and the file is ready for later phases. `error_code` is one of `unreadable_file`, `encrypted_file`, `too_many_pages`, `no_text`, `invalid_encoding`, `text_too_large`, `file_missing`, `source_missing`, `unsupported_file_type`, `timeout`, `internal_error`; `error_message` is a fixed, user-safe sentence (never exception text, content or paths). Extracted text is **not** returned by any endpoint. Upload returns `201` with `status: pending`; extraction runs in a background worker.

## 3. Documents ✅ (Phase 3)
Identical to resumes under `/documents` (`POST /documents`, `GET /documents`, `GET /documents/{id}`, `POST /documents/{id}/retry`, `GET /documents/{id}/file`, `DELETE /documents/{id}`), except: allowed types are PDF, DOCX and TXT (UTF-8), max 20 MB by default. `title` / `doc_type` fields are deferred.

**Upload validation (server-side, all required):** extension allow-list per kind; declared `Content-Type` must not contradict the extension (missing/`application/octet-stream` accepted); file signature checked (PDF header + `%%EOF`; DOCX = valid ZIP with `[Content_Types].xml` and `word/document.xml`, bounded entry count/size, no macros; TXT = valid UTF-8 without NUL bytes); size enforced while streaming plus an early body-size limit. Limits come from `RESUME_MAX_UPLOAD_MB` / `DOCUMENT_MAX_UPLOAD_MB`. Malware scanning is not implemented yet.

## 7. Operational
`GET /health` (liveness, no auth), `GET /ready` (dependency readiness, no auth), `GET /metrics` (Prometheus text, no application auth; expose only on a trusted monitoring network). Metrics are process-local; scrape each API process.

**Security headers (Phase 13A, D-54):** every HTTP response carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (omitted on `/docs` and `/redoc`). `/api/v1/auth/*` responses also carry `Cache-Control: no-store`. A header a route sets itself (for example the file download's `Cache-Control: private, no-store`) is not overwritten. HSTS is the TLS proxy's responsibility.

## 8. WebSocket (Phase 9A ✅ handshake, heartbeat, limits; 9B ✅ Q&A, cancel, backpressure; 9C ✅ resume; Phase 9 accepted)
Endpoint: `GET /api/v1/ws/sessions/{session_id}?ticket=<single-use>` over WSS (obtain the ticket with `POST /auth/ws-ticket`). Frames are **JSON text** envelopes `{ "type": "...", "id": "...", "seq": n, "ts": ms, "payload": {...} }`. Binary frames are not supported in Phase 9 (audio is a later phase); a binary frame closes the socket with `1003`. Contract source of truth: the Pydantic models in `app/realtime/schemas.py`, exported to `packages/protocol/protocol.schema.json` and `packages/protocol/src/index.ts` (generated, committed, drift-tested; regenerate with `python -m app.realtime.codegen` from `services/api`).

**Envelope.** Server messages: `type`, `id` (random hex message id), `seq`, `ts` (epoch milliseconds), `payload`. Client messages: `type`, optional `id` (≤ 64 chars, a correlation id of the client's choosing), `payload`; unknown fields are rejected. **Control events** (`session.ready`, `pong`, `error`) carry `seq: 0` and are never buffered or replayed. **Sequenced events** (the Q&A events, from 9B) carry a per-(user, session) channel `seq` ≥ 1 that increases by one per event; a client that reconnects sends `resume_from_seq` (the last `seq` it processed) in `client.hello`.

**Handshake.** All checks run before the socket is accepted, and every failure is the same bare refusal (HTTP `403`, no body): `Origin` present but not in `CORS_ORIGINS` (clients without an `Origin` header, such as the desktop app, pass), missing/garbage/expired/already-used ticket, a ticket issued for a different session than the path, a user that is missing or not active, a session that is not the ticket user's, a malformed session id. Identity comes only from the ticket. After accept the server sends `session.ready`; the client must answer with `client.hello` within `WS_HELLO_TIMEOUT_SECONDS` (default 10).

**Connection rules.** One socket per (user, session): a newer connection supersedes the older one, which is closed with `4001`. At most `WS_MAX_CONNECTIONS_PER_USER` (3) / `WS_MAX_TOTAL_CONNECTIONS` (200) sockets: beyond that the socket is accepted, receives a fatal `error too_many_connections` and is closed `4429`. Heartbeat: the client sends `ping` about every 20 s (`WS_HEARTBEAT_INTERVAL_SECONDS`, advertised in `session.ready`), the server answers `pong`; any received frame resets the idle clock; `WS_IDLE_TIMEOUT_SECONDS` (45) of silence closes `4002`. Frames larger than `WS_MAX_FRAME_BYTES` (16 KiB) close `1009`; more than `WS_MAX_MESSAGES_PER_SECOND` (10) close `4005`. **Backpressure (9B, reworked in 9C):** generation never waits for a socket. Sequenced events are appended to the per-(user, session) retained buffer (`WS_RESUME_BUFFER_EVENTS`, 2000 events and an internal 2 MiB budget, oldest dropped first); each connection's single writer reads that buffer at its own pace. Control messages (`pong`, `error`) wait in a small per-connection queue of at most `WS_SEND_QUEUE_EVENTS` (1000). A client is a *slow consumer* and the socket is closed `4010` when it falls behind the oldest retained event, when its control queue is full, or when a single send does not complete within `WS_SEND_TIMEOUT_SECONDS` (10). A slow-consumer close does NOT cancel the answer: it detaches like any other disconnect (see Resume). All limits are per API process (R-14, R-38).

**Close codes.** `1000` normal; `1003` binary frame; `1009` frame too large; `4001` superseded by a newer connection; `4002` idle timeout; `4003` protocol error (first message is not `client.hello`, duplicate hello, hello timeout, or too many invalid messages); `4004` unsupported protocol version; `4005` message rate exceeded; `4010` slow consumer (9B: the client does not read fast enough; the socket is closed without further events; since 9C the generation keeps running detached and the client can resume); `4429` connection limit; `1008` policy violation, used after accept only when the account is no longer active (the handshake refusal is the pre-accept `403`). On a process shutdown uvicorn itself closes sockets with `1012`.

**Q&A over WebSocket (9B, D-42).** `question.submit` runs the same core as `POST /sessions/{id}/questions` (`QuestionAnswerer.ask`): the same validation, ownership check, 409/422 refusals, per-user rate limit and concurrent-generation cap (shared with SSE), and the same persistence. Identity and the session come only from the ticket; the message carries only the text and the optional type. The server sends the sequenced events `question.created`, `retrieval.done`, `answer.started`, `answer.delta`..., then exactly one terminal event: `answer.done`, `answer.error` or `answer.cancelled`. Their payloads are identical to the SSE events (parity-tested). A refusal before the stream starts (unknown/foreign session, session or materials not ready, invalid text, rate limit, concurrency cap) is a non-fatal control `error` (`seq` 0) with the same code as the REST status, and no sequenced event. The user's active status and the session's ownership are re-checked on every `question.submit`. Only one generation per socket is active: another `question.submit` is refused with `error generation_in_progress` and never cancels the running one. `answer.cancel {question_id}` cancels the running generation: the answer is stored `cancelled` with its partial text, the slot is released, and `answer.cancelled` is sent. A cancel for any other question id (unknown, someone else's, already finished) is the single non-fatal `error nothing_to_cancel`, which does not distinguish those cases; a completed answer is never downgraded. The generation belongs to the (user, session) channel, not to the socket (9C): it keeps running when the socket closes, and a socket that reattaches may cancel it. If the answer had already completed when a cancel arrived (the cancel lost the race with the final commit), the stored completed answer wins: the server sends `answer.done`, rebuilt from the stored row, instead of `answer.cancelled`. The database is the source of truth for the terminal state of every answer; events are only delivery.

**Resume (9C, Option A, D-41/D-43).** One *channel* exists per (user, session). It owns the sequence counter, the bounded retained buffer of sequenced events and the single active generation; it is created on the first `question.submit` or connection and keyed only by identity taken from the ticket, so no client can address another user's channel. A socket attaches to the channel when its `client.hello` is accepted. When the socket closes for any reason (network loss, `4010`, supersede by a newer socket, client close) the channel detaches: a running generation CONTINUES and its events keep going into the buffer, for `WS_RESUME_GRACE_SECONDS` (30). A channel that has never carried an event is dropped at once. If nobody reattaches within the grace period the generation is cancelled (the partial answer is stored `cancelled`, the slot is released) and the buffer is freed; the same happens at server shutdown and when more than `WS_MAX_TOTAL_CONNECTIONS` channels are detached (oldest first).

A reconnect sends `resume_from_seq` (the last `seq` it processed) in `client.hello`. If the channel still holds every event after that number, the server replays them in order, byte-for-byte as first sent (same ids, same `seq`), and continues live with no gap and no duplicate. `resume_from_seq` equal to the channel's last `seq`, or absent/`0`, replays nothing. The non-fatal `error resume_unavailable` is returned, with no replay, when the channel no longer exists (grace expired), when the requested events have been dropped from the buffer, or when `resume_from_seq` is greater than the channel's last `seq`; the client then resyncs through `GET /sessions/{id}/questions` and treats `session.ready.resume_seq` as its new baseline (a channel that expired restarts at `seq` 1). A reconnect without `resume_from_seq` simply continues live. A running generation is visible to every socket of the channel: a new `question.submit` while one is active, from any socket, is refused with a non-fatal `error generation_in_progress` and never cancels it. A terminal event missed while detached (for example `answer.done`) is replayed from the buffer; the answer itself is always available from the history endpoints.

Versioning: `/api/v1` path; additive changes only within a version; WS `client.hello` carries `protocol_version`. Contract source of truth: FastAPI OpenAPI schema (REST) + JSON Schema/Pydantic models for WS events, with generated TS types in `packages/protocol/`.
